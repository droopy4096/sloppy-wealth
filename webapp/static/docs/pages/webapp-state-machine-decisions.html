Event emitters (2026-11-10, user decisions on EMITTERS_FEASIBILITY.md)

Form inputs become event emitters: event-producing factories with their own rules. The Scenario walks the date range over the Household (main object), asks emitters for events and applies them.

#QuestionDecision
D-E1Modifiers (renewal, extraPayment, lumpSum on a mortgage; sale, improvement, marketAdjustment on an asset)Separate emitters attached to their host, timed at the host's position; the form groups them under their host. One form input = one emitter.
D-E2How the loop collects eventsOrder number built into each emitter class (instance may override). The Scenario sorts all emitters by order (ties: scenario item index) and splits them into as many phases as it needs; each month it walks the sorted list, asks each emitter for events and applies them immediately, so later emitters see earlier state. Reordering = changing a number. An item acting at several points of a month (e.g. mortgage advance vs servicing) yields several emitters with their own orders. Defaults reproduce today's 17-phase order (parity).
D-E3Sale and secured loansFollow-up events: the sale event emits a payoff event per secured loan, then the penalty, applied immediately; each loan settles itself.
D-E4Event logPublic: run_detailed() gains an events key and the app a view of it. A deliberate interface addition; rows, holdings, ledger and tax stay identical, the diff harness ignores events.
