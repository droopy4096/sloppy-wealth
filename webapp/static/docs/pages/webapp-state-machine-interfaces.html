State-machine engine: interfaces (WP1–WP9, emitter model E0–E7)

References to engine.py / "the reference" point to iteration 1 on branch poc/python-flask (tag poc-iteration-1).

The engine is an event-emitter model (D-E1..D-E4): item factories build emitters (§4, §6), the ScenarioRunner walks them by order key every month (§5) and applies their events, logging each one (§10.7). §10 is the detailed contract. The pre-emitter clock handlers (Handler, Event, Process, InitialEvent, Phase) and their adapter were removed in E7 (§10.8).

Binding for every work package. Inputs: DECISIONS.md (D1–D5), FEASIBILITY.md (§2 phases, §6 packages), OBJECTS.md (formulas, ledger kinds, hazards: read the section of your WP there before coding). The reference is webapp/engine.py; repr(run_detailed(s)) and validate errors must be identical.

5. Order key and the month loop (clock.py, runner.py)

ScenarioRunner (runner.py) holds every registered emitter. run(household):

  1. INITIAL step: every emitter with a negative order, in key order, asked due(None) / emit(None, household) (household.month is None; no movements).
  2. Each month m of the horizon: household.begin_month(m) (core OPEN step: month, tax reset, opened/opening snapshots), then every emitter with order ≥ 0 whose due(m) is true, sorted by the order key (order, ordinal, sub). Each event is applied as soon as it is produced, its follow-ups depth-first (§10.5), and logged.
  • order: a clock.Order number (table in §10.2) or any int between two of them (Order.SERVICE_DEBT + 50). The numbers are ORDER_STEP (100) apart and reproduce the reference's intra-month step order.
  • ordinal = ctx.ordinal, assigned by the compiler: the item index; for a holding item the slot (index of the first holding item with that id); for a modifier at its host, the host's slot (§10.4). Scenario-level emitters (setup hooks) get SCENARIO = -1.
  • sub disambiguates two emitters at one (order, ordinal) (class SUB, instance sub=, or sub_order(stage, index) for modifiers).
  • A duplicate key raises ValueError at registration; registering anything that is not an emitters.Emitter raises TypeError. runner.schedule() lists the keys, runner.steps() groups emitters by order number.

Contribution room (ADR-0060) runs at order OPEN+50 (after the retirement event, before income) at its item's ordinal: sub 0 RoomStartEmitter, sub 1 RoomYearEmitter.

Cash balance (ADR-0063) runs at order TAX+50 (after the tax step, before CLOSE) at its item's ordinal; cash flow adjustments (ADR-0062) log at OPEN+60.

Scenario-level subs: OPEN/-1/n RetirementEmitter of the n-th person (ADR-0061; 0 with one person); TAX/-1/0 TaxEmitter (one step for every person); CLOSE/-1/0 results Recorder. Pick a free sub for any new scenario-level emitter.

Every module in holdings/, flows/, events/, rules/ and results.py is imported by discover() before the first compile; just create your file. The compiler sets each emitter's ordinal (ctx.ordinal, or the host's slot for a modifier), index (ctx.index; None for setup hooks) and source (ctx.id unless the emitter set one). After every factory has run it calls emitter.prepare(env) for all emitters in key order (cross-item facts, §10.3).

ItemContext ctx: item (raw dict), index, id (item.get("id") or f"item{n}"), ordinal (use as the aggregate's item_index), name (item.name or id), household, env (CompileContext). CompileContext env: scenario, items, household, runner, start, end, retirement (month or None), retirement_date, properties ({id: property item}, last wins, for mortgage_start), sales (property_sales(items, retirement_date)), slot, owner, emitters_for(item_id), modifiers_of(host, cls=None) (valid in prepare), and bucket(name, key) -> list (shared list between factories; no production module needs it any more).

Compile rules:

  • Factories run in item order; holding types (HOLDING_TYPES) are compiled only for the last item with a given id, at the first item's slot (reference dict semantics).
  • Factories never move money and never add aggregates (D1: events create them, at INITIAL or later). Read-only use of household settings is fine.
  • Resolve retirement anchors at compile time from env.retirement exactly as prepare() does (startsAtRetirement, endsAtRetirement → last = min(last, retirement-1), blank start of pension/withdrawal, atRetirement of sale/lumpSum/transfer). household.retired is for the tax rate only.
  • The retirement item type yields nothing: the setup hook wp7.retirement_tax yields one RetirementEmitter per person with a retirement, and the TaxEmitter.
  • Older input forms (scenario retirementDate, a property's own saleDate, withdrawal method even, monthlyAmount) are converted by upgrade.upgrade(scenario), called at the start of validate and compile_scenario; the rest of the engine knows only the current forms. A converted retirementDate outside the horizon is an event with outsideHorizon: true.
  • compile_scenario(scenario) -> (household, runner); it does not validate.
  • Tests: with compiler.isolated_registry(): ... gives an empty registry (restored after).

# emitters.py

                                            # FlowEvent "flow", ValuationEvent "valuation",

    SUB = 0
    def __init__(self, schedule=None, *, order=None, sub=None, source=None)

    emit(month, household) -> iterable[Event] | None   # may READ state, never write it

10.3 How a factory returns emitters

@item_type("income")
def compile_income(item, ctx):                 # unchanged registration (§6)
    yield IncomeEmitter(first, last, ...)       # ordinal = ctx.ordinal, source = ctx.id,
                                                # index = ctx.index: all set by the compiler
@scenario_setup("tax", order=50)
def setup_tax(env):
    yield TaxEmitter()                          # ordinal SCENARIO, source None, index None
  • A factory returns Emitters only (anything else: TypeError at registration).
  • Two emitters of one item at one order need distinct subs (duplicate key → ValueError).
  • source defaults to ctx.id; pass source= to override (e.g. a property's own legacy saleDate sale uses the asset id, as today).
  • Retirement anchoring (startsAtRetirement, endsAtRetirement, atRetirement, blank pension start) stays resolved at compile time from env.retirement, as today.
  • After every factory has run the compiler calls emitter.prepare(env) for all emitters in key order. Lookups available there: env.emitters_for(item_id) (emitters with that source, key order) and env.modifiers_of(host, cls=None) (modifiers of a host, item order). env.bucket still exists, but no production module uses it.

10.4 Modifiers attached to a host (D-E1)

class RenewalEmitter(ModifierEmitter):
    ORDER = Order.SERVICE_DEBT       # the order of the host action it modifies
    STAGE = 0                        # 0 before the host's own step, 2 after, ...
    def __init__(self, item, ...): super().__init__(item["mortgage"], Once(month), ...)
  • host = the host item id. AT_HOST = True (default): the compiler sets ordinal = env.slot[host] (the host holding's slot; unknown host → ValueError); AT_HOST = False: own item index (improvement, marketAdjustment: the reference loops items there, not holdings).
  • sub defaults to sub_order(stage, own item index): modifiers of one host sort by stage, then item order. The host's own emitter at that order uses sub=sub_order(1) (or any stage between its modifiers' stages).
  • Mortgage (E2): renewal stage 0 → service stage 1 (gate, accrue or settle + interest + payment) → extraPayment/lumpSum stage 2 in item order. Hazards to keep:
    • Last renewal in a month wins: in prepare, a renewal finds its siblings via env.modifiers_of(host, RenewalEmitter) and is due only if no later sibling has the same month.
    • The gate is the service's: renewal and extras run only if the loan existed and was opened at the start of the month and balance > 0 when service starts; extras also not while accruing (month < first_pay). A lump sum's penalty is charged even when its prepayment rounds to 0, also after the last payment cleared the balance — so extras must not re-test balance > 0 after the payment. Have the service emitter record the month it serviced (e.g. on its host emitter, found via env.emitters_for(host)) and let stage-2 modifiers test that.
  • Sale (E1): a ModifierEmitter with host = the asset (AT_HOST, ORDER SELL). Exactly one sale per asset (dates.property_sales raises otherwise); an older file's property saleDate arrives as a sale item (upgrade.py).

10.5 Follow-up events (D-E3)

Event.apply returns follow-ups; the runner applies each immediately, depth-first, before the next event of the same emitter (and before the next emitter). Follow-ups inherit the parent's key and source unless they set their own, and are logged with cause = the parent's log index. Sale:

class Sale(LifecycleEvent):
    def apply(self, hh):
        ... SALE_PRICE_DIFFERENCE, SALE, capital gains, SELLING_COST (as today) ...
        return [LoanPayoff(loan.id) for loan in hh.loans_secured_by(self.asset_id)
                if loan.balance] + [SalePenalty(self.penalty)]
class LoanPayoff(LifecycleEvent):           # the loan settles itself
    def apply(self, hh): hh[self.loan_id].pay_off(hh, self.source)

Ledger order stays SALE…, SELLING_COST, LOAN_PAYOFF per loan (holdings order), PENALTY.

10.6 State-dependent amounts

Compute every amount that depends on balances in apply, not in emit: the household changes within the month (a sale pays a loan before servicing, a contribution lands before a withdrawal, tax needs the month's accumulator). emit decides whether and what (gates, schedule, strategy); apply resolves how much and calls household.move. emit may be a generator: each yielded event is applied before the generator resumes, so later events of one emitter see the earlier ones' effect. Rounding, zero-move and Decimal('0') vs Decimal('0.00') quirks stay where they are today (in move and the aggregates' methods). Emit nothing in months where nothing happens (the log should only hold events that did something or changed state).

10.8 The legacy adapter (removed in E7)

From E0 to E6 ScenarioRunner.register wrapped old clock handlers (base.Handler: Event, Process, InitialEvent, each declaring a clock.Phase) in a LegacyEmitter at order Order[phase.name] that emitted one opaque legacy event per firing. Once every factory returned emitters, E7 deleted the adapter, the handler classes, clock.Phase, MONTHLY_PHASES and order_of_phase; clock.Order keeps the same numbers (former phase × 100). register now raises TypeError for anything that is not an Emitter, and no legacy kind appears in the event log. Old name → new: phase → Order number; Event (dated) → OneShotEmitter + an Event subclass; Process → RecurringEmitter; InitialEvent → InitialEmitter; runner.phases() → runner.steps(); env.clock → env.runner.
